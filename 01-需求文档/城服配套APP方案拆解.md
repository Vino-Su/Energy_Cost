## 1 城服项目工种

城服项目组织中涉及人员类型较多，但是总体可以分为三大类：

1. **管理层：** 项目经理、片区经理、主管、人工作业经理、机械作业经理、品质经理
2. **一线作业人员：** 环卫工（保洁员、机动工、水车工、大件工、公厕保洁员、辅助工、操作工等）、驾驶员、安全员、品质巡查员
3. **辅助类：** 项目文员
其中，管理层主要负责某一具体业务，需要关注团队的人员情况、任务分配及完成情况等，一线作业人员则大多是任务驱动制，负责执行管理层分配的特定任务，辅助类则偏向于台账和考勤等材料的整理以及团队后勤。

## 2 对于 APP 的需求

APP 的定位是能够便于项目人员能够随时随地的进行便捷办公，同时兼顾项目监管的功能，根据不同人员类型的特点，得出不同人员类型对 APP 的需求

### 2.1 管理层

管理层一般不进行具体任务的执行，主要关注的对于项目/特定业务整体情况的把握，具体的可以包含：

#### 2.1.1 项目经理、片区经理

目标：掌握项目经营和履约情况

主要关注：人员到岗、任务完成率、车辆利用率、事件处置、费用成本、项目人员排名

#### 2.1.2 作业经理、主管

目标：组织当天生产作业

主要关注：排班、任务分派、进度跟踪、异常处理、任务完成情况

#### 2.1.3 品质经理

目标：保障服务质量

主要关注：巡查计划、问题分布、整改时效、复查结果、考核扣分

### 2.2 一线作业人员

一线作业人员总体都是任务驱动制的工作模式，往往只关注于与自身相关的信息，如考勤、待办任务等功能。具体的，根据不同作业类型，又可以细分为以下几类

#### 2.2.1 司机类

主要负责驾驶作业车辆，其作业模式需要与车辆进行强关联，共同完成任务

```
开始 ——> 绑定车辆 ——> 查看今日任务 ——> 开始任务 ——> 执行任务 ——> 水电油上报 ——> 完成任务 ——> 交车 ——> 结束
```

对于 APP 而言，需要支持司机类人员以下需求

- 支持员工的考勤打卡
- 支持任务的接受、执行和完成
- 支持车务相关活动的上报
- 支持查看车辆信息
#### 2.2.2 环卫工类

主要负责环卫相关的人力活动，根据具体业务的不同，工作内容不同，但是其基本流程相同，目的是快速完成个人任务

```
开始 ——> 上班打卡 ——> 查看今日任务 ——> 开始任务 ——> 执行任务 ——> 事件上报 ——> 完成任务 ——> 下班打卡 ——> 结束
```

对于 APP 而言，需要支持环卫工类人员以下需求

- 支持员工的考勤打卡
- 支持任务的接受、执行和完成
- 支持事件的上报
#### 2.2.3 巡查类

主要负责进行品质巡查，对其他工种完成情况进行考评和监督，发现并推动问题整改。考虑到巡查人员任务中的检查项和判定标准与环卫工类不同，因此流程不建议复用

```
开始 ——> 上班打卡 ——> 查看今日任务 ——> 开始任务 ——> 执行任务 ——> 事件上报 ——> 完成任务 ——> 下班打卡 ——> 结束
```

注意一点，巡查人员一般也会与车辆关联，分为两轮电动车和机动车，其中机动车部分任务模式又与司机类人员的工作模式类似。

对于 APP 而言，需要支持巡查类以下需求

- 支持员工的考勤打卡
- 支持任务的接受、执行和完成
- 支持事件的上报、整改复查
#### 2.2.4 安全员类

主要负责远程监管机器人的状态，保障机器人与现场的安全。若收到应急工单，及时到场救援

```
开始 ——> 上班打卡 ——> 机器人状态监控 ——> 处理应急工单 ——> 故障报修 ——> 完成工单 ——> 下班打卡 ——> 结束
```

对于 APP 而言，需要支持安全员类以下需求

- 支持员工的考勤打卡
- 支持应急工单的接受、执行和完成
- 支持事件的上报
- 支持查看机器人信息
### 2.3 辅助类

主要负责处理一些项目辅助事项，如台账整理、考勤统计、费用录入等功能，其主要工作应该是在 WEB 端开展，APP 仅作为辅助工具。

## 3 对 APP 架构的考虑

综合以上分析，城服项目中对 APP 的使用涉及到项目全部人员，一方面，管理层能够对任务、事件等进行派发和管理，另一方面，一线作业人员接收到管理层派发的任务并执行后，将任务完成数据再展示给管理层，并根据业务需求形成各种的统计报表，用来监控项目的健康情况。其整体业务功能总体可以分为几个层次：

- **人：** 员工信息、考勤打卡、作业排班情况、加班记录、异常处理、作业培训等
- **设备/资产：** 车辆管理、机器人管理
- **任务/事件：** 常规任务、动态任务、巡查任务、事件上报、应急工单、异常记录
- **费用/成本：** 费用上报、费用报销
- **数据统计：** 工作日报、考勤统计、任务统计、费用统计等
- **实时监控：** 车辆实时监控、人员实时监控、作业实时监控

针对不同的人员类型，进行针对性的 APP 应用的开发，需要秉持的原则是：功能不重复开发，提高页面的可重复使用率；不同人员进入 APP 能够明确各自的任务

具体的，APP 的功能架构层面，APP 的入口层可以分为首页、地图及服务三个版块：

### 3.1 首页

管理人员的主页面，支持用户自定义功能的快捷方式，支持展示项目的核心数据

主要功能：待办事项、快捷入口、业务提醒等

### 3.2 地图

现场人员的主页面，支持现场人员进行任务查看、执行和轨迹上报，同时也能作为管理人员全局监控和调度的载体

主要功能：

- 任务执行、事件上报、车辆管理、机器人管理、实时监控等
- 图层、作业路线、轨迹、导航等地图基础能力
实现路径：
地图模块涉及到多个角色的使用，不同角色的使用场景及关注点都存在差异。
建议采用：
- 地图页 = 统一底图 + 角色场景化图层 + 角色场景化操作面板
- 角色之间通过「场景切换」流转，而非退出重登
- 图层可叠加（信息可同时看），操作面板互斥（动作只能做一个）
即用户如果只有一种角色，则默认打开的地图是针对性的地图，可以直接进行相应业务
如果用户有多种角色，则默认显示上次登陆的角色，支持手动切换，此时地图的页面根据选中的角色进行显示，不支持一次性显示多种角色的操作。

### 3.3 服务

围绕着城服项目所涉及到的人员类型及场景，集成所有的功能域，并支持按照不同的角色进行权限控制，确保不同角色用户能够看到各自针对性的功能

| 功能域   | 主要功能                      |
| ----- | ------------------------- |
| 人员与考勤 | 员工信息、考勤打卡、排班、加班、考勤异常      |
| 作业任务  | 常规任务、动态任务、巡查任务、任务派发、执行与跟踪 |
| 事件管理  | 事件上报、事件派发、处置跟踪、结果反馈       |
| 品质管理  | 巡查任务、问题上报、问题派发、整改与跟踪、考评结果 |
| 车辆管理  | 车辆查看、车辆绑定/交车、车务活动上报       |
| 机器人管理 | 状态查看、告警信息、故障报修            |
| 应急工单  | 工单接收、现场救援、处理反馈、工单完成       |
| 费用成本  | 水电油上报、其他费用上报、费用报销         |
| 实时监控  | 人员、车辆、机器人和作业任务的实时状态       |
| 数据统计  | 考勤、任务、工作日报、事件、费用及资产统计     |
